## Why I came here

This is the guided exploration command — the one that walked me through starting this very journey. The example journey reference has to be in here, because that's what I saw in the start output.

## What I found

The file is a state machine. A mind's exploration has a status (`new` → `research_logged` → `planned` → `embarked` → `reflected` → back to `planned` or done), and each `--flag` advances the state. Clean design — each step is a small function.

**The example journey reference** lives at line 272, in `_find_example_journey()`:
```python
example = ctx.paths.pkgs.current.assets_dir / "chart" / "example-journey"
```
It looks in the *current package's* assets directory. `ctx.paths.pkgs.current` — that means whichever package owns the command being run (haiv-core, in this case). The result is passed to `explore-start.md.j2` on line 161.

The docstring has a telling comment: `"Projects can override this via hook (TODO)."` So the original author knew this needed to be project-configurable. They left a hook-based approach as a TODO, but my assignment takes a different path — project-local folder in the atlas itself.

**Key insight:** The example journey is only used in one place — `_do_start()`, line 161. It's passed to a template. That's the entire surface area of my change. Small.

**Something I didn't expect:** The state is stored per-mind in `mind.work.exploration_file`, not in the atlas. This means multiple minds can explore simultaneously without conflict. Smart.

**Another thing:** `_journey_dir()` on line 49 uses `ctx.paths.atlas.journeys_dir / name`. The atlas paths are already being used here. If I add an examples concept to `AtlasPaths`, this command is already wired to use it.
