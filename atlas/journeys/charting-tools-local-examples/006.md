## Why I came here

I need to understand the helper pattern before deciding whether to extract chart/example logic into a helper. This is one of the established helpers, and `explore.py` already imports from it.

## What I found

The pattern is clear. A helper is:
- **A module of standalone functions** that take explicit parameters (usually a `Path` to a file or directory, plus domain data). No classes with state, no singletons.
- **Focused on one domain concept.** This file is entirely about sessions — creating, loading, finding, updating, removing them. It defines a `Session` dataclass and every function operates on sessions.
- **No awareness of commands.** Functions take `sessions_file: Path`, not `ctx: cmd.Ctx`. They don't know which command called them. This is what makes them reusable — any command (or another helper) can call them.
- **Lives in `haiv-lib/src/haiv/helpers/`.** The `haiv/` package namespace, not `haiv_core/`. So helpers are available to all packages, not just core.

The key insight: helpers are the *domain logic* layer. Commands are the *user interaction* layer. Commands decide what to show and when; helpers do the actual work.

**How this applies to my task:** If the "find or create example journey" logic is shared between `_index_.py` and `explore.py` (or could be in the future), it belongs in a helper. The helper would take atlas paths and asset paths as arguments, handle the "check if exists, copy from template if not" logic, and return the example path and file list. Both commands would call it.

But is there really enough shared logic to justify a helper? Let me think about what the helper would do:
1. Check if project-local examples folder exists
2. If empty/missing, copy from bundled assets
3. Return the path and list of files

That's maybe 10-15 lines. Small, but it's logic that shouldn't live in a command (it's domain knowledge about atlas structure, not user interaction). And it would be called from at least two places if `_index_.py` also ensures the folder exists.
