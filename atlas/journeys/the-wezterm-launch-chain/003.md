# 003 — The Terminal Manager

**File:** `worktrees/main/haiv-lib/src/haiv/helpers/tui/terminal.py`

## Why I came here

This is where `ctx.tui.start()` resolves to. The TerminalManager orchestrates WezTerm — launching it, creating tabs/windows, splitting panes, swapping minds. This is where the process tree branches.

## What I found

`ensure_workspace()` (line 172) is the entry point for `hv start`. Four cases:

| In WezTerm? | Hud tab? | TUI pane? | Action |
|-------------|----------|-----------|--------|
| No | — | — | `_launch_wezterm()` — spawn a new WezTerm instance |
| Yes | No | — | `_create_window()` — new window with TUI + empty mind pane |
| Yes | Yes | Yes | Already healthy, just activate |
| Yes | Yes | No | `_recover_tui()` — TUI crashed, recreate its pane |

**Case 1: `_launch_wezterm()` (line 346)**

```python
self.wezterm.run_external(
    ["start", "--cwd", str(self.haiv_root), "--"]
    + self._shell_wrap(["hv", "start"]),
)
```

This runs `wezterm start -- bash -c "hv start; exec bash"`. WezTerm opens, runs the shell command inside a pane. That inner `hv start` detects it's inside WezTerm (TERM_PROGRAM=WezTerm) and hits case 2.

**Case 2: `_create_window()` (line 375)**

Uses `wezterm cli spawn --new-window` to create a second window, then `wezterm cli split-pane` for the mind pane. These are IPC calls to the WezTerm server — not subprocess spawns from our process.

**Case 4: `_recover_tui()` (line 358)**

Splits the surviving pane to create a new TUI pane. Uses `wezterm cli split-pane` with the `tui_command`.

**`launch_in_mind_pane()` (line 58)** — how minds get spawned. Calls `wezterm.split_pane()` to create a pane, then `wezterm.send_text()` to type the claude command into it. Claude Code is spawned by WezTerm's shell, not by haiv.

## Process lifecycle — what the code proves

- **Original `hv start`** (outside WezTerm): calls `run_external()`, which on Windows uses `Popen` with `DETACHED_PROCESS`. The calling process exits. **Dies.**
- **WezTerm #1**: opens, runs `bash -c "hv start; exec bash"` in a pane.
- **Inner `hv start`**: runs inside WezTerm #1, calls `_create_window()` which uses `wezterm cli spawn --new-window`. Then exits. **Dies.**
- **WezTerm #2 (or second window)**: created by `wezterm cli spawn --new-window`. Contains the TUI and mind panes.

## What we cannot prove from code alone

- **What is the actual process hierarchy on Windows?** WezTerm's logical architecture (server/client IPC) is separate from its process hierarchy (parent/child tree). A job object operates on the hierarchy. WezTerm could use one process, multiple processes reporting to one server, separate GUI processes per window — any arrangement. The process hierarchy determines whether a job object can capture everything, and we can only learn it by observing on Windows.
- **Why does the first window linger on Windows but not Linux?** Different lifecycle behavior. Could be shell exit behavior, could be WezTerm's process management differing by platform.
- **Who are the parent processes of pane shells?** `wezterm cli` commands are IPC to a server, but the server might spawn panes as its own children, delegate to a GUI process, or something else entirely. This is a WezTerm implementation detail that varies by platform.

## The orphan problem — what we know

- On Windows, closing WezTerm leaves child processes (Claude Code sessions, TUI) running as orphans.
- On Windows, the first WezTerm window does not close automatically (unlike Linux).
- All pane processes are spawned by WezTerm, not by haiv — our process tree doesn't include them.
- The `DETACHED_PROCESS` flag in `run_external()` was added to decouple the WezTerm launch from the calling terminal.
