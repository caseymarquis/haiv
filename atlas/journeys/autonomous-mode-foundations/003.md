# 003 — The Staging Command

**File:** `worktrees/main/haiv-core/src/haiv_core/commands/minds/stage.py`

## Why I came here

Now that I understand the session data layer, I need to see where sessions get created in the staging flow — and more importantly, where worktree creation happens and how it interleaves with everything else.

## What I found

The command is 238 lines and cleanly structured. Here's the full flow:

**Flags defined (line 33):**
- `--task` (required) — short summary, 72 char max
- `--description` — longer context
- `--name` — mind name (optional, auto-generated if missing)
- `--from-branch` — base branch (auto-detected from parent session if missing)
- `--allow-dirty` — skip clean working tree check

**Execute flow (line 77):**
1. Validate `--task` (required, length check)
2. **Mind reuse** — if no `--name` given, looks for existing minds without active sessions and picks one at random. This is interesting — minds are recycled, not always created fresh.
3. Get or generate mind name (reuse > explicit > auto-generate)
4. Validate name (skipped for reused minds)
5. Determine base branch (`--from-branch` or detect from parent session)
6. Check clean working tree (unless `--allow-dirty`)
7. **Create worktree** (line 141) — `git worktree add -b {name} worktrees/{name} {base_branch}`
8. **Emit hook** (line 148) — `AFTER_WORKTREE_CREATED` with worktree path, branch, base_branch, mind_name
9. **Scaffold mind** (line 160) — `scaffold_mind()` with `location` string and `skip_existing` for reused minds
10. **Create session** (line 169) — status "staged", with branch, base_branch, parent_id from HV_SESSION env
11. Refresh TUI
12. Print guidance (edit welcome.md, assign role, `hv start`)

## What surprised me

**The worktree name IS the branch name.** Line 142: `git worktree add -b {name} worktrees/{name} {base_branch}`. The mind name, the branch name, and the worktree folder name are all the same string. This tight coupling means "optional worktree" isn't just about skipping `git worktree add` — it's about what happens to branch identity when there's no worktree.

**Mind reuse is the default path.** If you don't specify `--name`, the system prefers reusing an idle mind over creating a new one. For no-worktree tasks, a reused mind would need its old worktree to be gone (or never created). This adds a wrinkle — reused minds might have worktree remnants.

**The `location` parameter to `scaffold_mind`** (line 163) is just a string passed to the welcome template. For no-worktree minds, this could be something like `"haiv-hq (no worktree)"` or omitted entirely.

**Session creation happens AFTER worktree creation.** The order is: worktree → hook → scaffold → session. If I want optional worktrees, I can gate step 7-8 on a flag and everything downstream still works. The session just won't have `branch`/`base_branch` set.

## What this means for my task

The insertion points are clear:

1. **New flags needed:** `--autonomous` (or `--mode autonomous`) and `--no-worktree`
2. **Worktree creation** (lines 132-156) can be wrapped in `if not no_worktree:`
3. **Session creation** (line 169) needs the new mode fields passed through
4. **Scaffold call** needs a different `location` when there's no worktree
5. **Output guidance** (lines 196-199) needs to adapt — no "Worktree:" line, different next steps for autonomous minds

The `--from-branch` and `--allow-dirty` flags become irrelevant when `--no-worktree` is set — should those be validated (error if both specified) or silently ignored?
