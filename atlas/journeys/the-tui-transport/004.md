# 004 — The Local Client

**File:** `worktrees/luna/haiv-lib/src/haiv/_infrastructure/TuiServer/_TuiLocalClient.py`

## Why I came here

I needed to see how the in-process client wraps the `submit()` pattern into the `ModelClient` protocol. This is the template for the command queue's push API.

## What I found

66 lines. Even simpler than I expected.

**The constructor takes only `submit`.** Not the server, not the model — just the `Callable[[Request], Future]`. This is the same boundary the IPC listener respects. Nobody outside the model thread can touch the model.

**`read()`** submits a `ReadRequest`, blocks on `future.result()`, then freezes the returned model via `freeze_model()`. The freeze step is interesting — reads get immutable snapshots.

**`write_raw()`** constructs a `TuiModel` with the provided sections (rest default to None), wraps it in a `WriteRequest`, submits, blocks on the future. Simple passthrough.

The pattern for command sending is clear: `send_command()` would construct a `CommandRequest`, submit it, block on the future. The server's model loop would handle `CommandRequest` by appending to a command buffer (an `Atom[list]` or similar), and `drain_commands()` would atomically swap it out — same pattern as dirty tracking.

## What surprised me

How thin this is. The client is really just a typed wrapper around `submit()`. All the intelligence is in the server's model thread. The client's job is purely "construct the right request type and wait for the answer."

Also: `freeze_model()` is imported from `_freeze`. The server returns a `deepcopy` (mutable), but the local client freezes it. The IPC client probably doesn't need to freeze because serialization already creates an independent copy. Nice asymmetry.
