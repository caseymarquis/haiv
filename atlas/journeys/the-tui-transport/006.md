# 006 — The Poll Loop

**File:** `worktrees/luna/haiv-tui/src/haiv_tui/app.py`

## Why I came here

Last stop. I needed to see how `drain_dirty()` is called and how dirty sections flow into the store. This is where `drain_commands()` will be called too.

## What I found

271 lines. The poll loop is clean and minimal.

**`_poll_model()`** (lines 147-159) runs every 0.1s via `set_interval`. It calls `self._server.drain_dirty()`, returns early if nothing changed, otherwise reads a frozen snapshot via `self.tui_client.read()` and pushes it through `self.store.update(snapshot, dirty)`. The store fires blinker signals per dirty section. Errors go to `self.internal_errors`.

**Command draining slots in naturally.** The poll loop already has the "drain → process" rhythm. Adding `drain_commands()` is a second drain step in the same loop — but commands bypass the store entirely. They're UI instructions, not data updates. The app would handle them directly, dispatching to widget methods or app actions.

**Constructor takes `server` and `client` explicitly** — no internal resolution. `_server` is private, `tui_client` is public (widgets use it to push data back). The server is started in `on_mount()` and stopped in `shutdown()`.

**Background workers** (`_Workers` class, lines 234-271) are data producers. They call `helpers.sessions_refresh()` and run a `RecentFilesWorker`, both pushing via the client. Commands flow the opposite direction — from outside into the TUI — so workers aren't involved.

## The full picture

I now have the complete transport mapped:

```
Producer (hv command / mind)
    → TuiLocalClient.write_raw() or TuiClient (IPC)
    → submit(WriteRequest) → queue
    → model thread: _apply_write() + mark dirty
    → poll loop: drain_dirty() → read snapshot → store.update() → signals → widgets

Command queue (new):
    → TuiLocalClient.send_command() or TuiClient (IPC)
    → submit(CommandRequest) → queue
    → model thread: append to command buffer
    → poll loop: drain_commands() → app dispatches directly
```

Two parallel channels through the same queue and model thread, diverging at the drain point. Data goes through the store. Commands go directly to the app.
