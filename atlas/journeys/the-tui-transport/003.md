# 003 — The Server

**File:** `worktrees/luna/haiv-lib/src/haiv/_infrastructure/TuiServer/_TuiServer.py`

## Why I came here

I needed to understand how `write_raw` data gets received and stored, and how the dirty-tracking mechanism works. This is the pattern the command queue's server side will mirror.

## What I found

234 lines. The threading model is elegant and stricter than I expected.

**The model thread is the only thing that touches the model.** No locks needed because there's no shared mutable state — just a single-threaded owner. Everyone else (IPC listener, local client) submits `Request` objects through a `queue.Queue`, gets back a `concurrent.futures.Future`. The model thread drains the queue, processes each request, and resolves the future.

**Two request types:** `ReadRequest` and `WriteRequest` (defined in `_TuiIpc.py`). Reads return a `deepcopy` of the entire model. Writes call `_apply_write()`, which iterates `dataclasses.fields(TuiModel)`, replaces non-None sections, and marks them dirty.

**Dirty tracking uses `Atom`** — a haiv utility for atomic modify operations. `_dirty` is an `Atom[set[str]]` holding section names that changed since last drain. `drain_dirty()` atomically swaps the set with an empty one and returns the old contents as a `frozenset`. Clean and race-free.

**The submit pattern is the key insight for command queue design.** Both IPC and local clients use the exact same `submit()` method. It doesn't matter where the request comes from — it goes through the same queue, processed by the same thread. This is how we can add commands: new request types in the queue, new handling in the model loop.

But wait — the model loop currently only knows `ReadRequest` and `WriteRequest`. Adding command requests here would mean the model thread processes commands too. That feels wrong. Commands aren't model mutations — they're instructions for the TUI app. They shouldn't go through the model thread at all.

**Alternative:** The command queue could be a completely separate channel — its own `Atom` or `queue.Queue` — that the poll loop drains independently. The server would have `submit_command()` alongside `submit()`, and `drain_commands()` alongside `drain_dirty()`. No model thread involvement. This keeps command delivery orthogonal to model state.

## What surprised me

The `Atom` utility. I expected a `threading.Lock` around a set. Instead, `Atom.modify()` takes a function and applies it atomically. Functional-style thread safety. I want to understand what `Atom` does internally, but that's a tangent — I'll note it for the quest board.

Also surprised by how explicit the separation is. The docstring spells out the threading architecture in detail. Two threads, neither managed by Textual. The model thread is "pure in-memory — microseconds." This discipline is why the system works without async.
