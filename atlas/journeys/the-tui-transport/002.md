# 002 — The Protocol

**File:** `worktrees/luna/haiv-lib/src/haiv/helpers/tui/protocol.py`

## Why I came here

This is the contract both clients implement. The command queue will be added here, so I need to see what shape the protocol has now.

## What I found

It's tiny — 27 lines. `ModelClient` is a `Protocol` with two methods:

- `read() -> TuiModel` — returns the full model snapshot
- `write_raw(*, sessions, git, active_mind, recent_files) -> None` — pushes individual sections, all optional keyword-only args

The protocol is `@runtime_checkable`, so isinstance checks work. It imports the raw section types from `TuiModel` and uses them directly in the `write_raw` signature.

## What surprised me

`write_raw` is tightly coupled to the current set of model sections. Every section is an explicit keyword argument — not a generic `**sections` or section-name-to-data mapping. This means adding a new section requires changing the protocol signature. That's a conscious choice: you get full type safety at every call site, but the protocol grows with the model.

For the command queue, this is important. Casey said commands should NOT be another TuiModel section — they're a separate channel. So the protocol needs a new method, something like `send_command(cmd)`. The existing `write_raw` pattern shows the preference: explicit types over generic containers.

Also notable: there's no `drain` or `poll` on the protocol. Those are server-side concerns. The protocol is strictly the *push* interface — "here's data, take it." The server decides when and how to make it available to the app. The command queue's push side will follow the same shape.
