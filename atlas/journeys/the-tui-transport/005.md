# 005 — The IPC Contract

**File:** `worktrees/luna/haiv-lib/src/haiv/_infrastructure/TuiServer/_TuiIpc.py`

## Why I came here

I needed to see the request types — `ReadRequest`, `WriteRequest`, and the `Request` union. This is where `CommandRequest` will be added.

## What I found

94 lines. Three concerns: address resolution, request/response messages, and errors.

**Request types are frozen dataclasses.** `ReadRequest` is empty (no payload). `WriteRequest` carries a `TuiModel`. Both are frozen — immutable once created. `Request = ReadRequest | WriteRequest` is a type alias union.

**Response types exist for IPC.** `OkResponse` (optional `TuiModel` result) and `ErrorResponse` (kind + message). These are used by the IPC transport (serialization across processes). The local client doesn't use them — it gets results directly through futures.

**`ConcurrencyError`** exists but the current `_apply_write` in TuiServer doesn't use it. The `WriteRequest` docstring says "version-checked merge" but the implementation just overwrites. Possibly a planned feature or vestige.

## Design implications for commands

Adding `CommandRequest` here is straightforward:

```python
@dataclass(frozen=True)
class CommandRequest:
    command: TuiCommand  # The typed envelope

Request = ReadRequest | WriteRequest | CommandRequest
```

The `TuiCommand` type (the envelope with type string + payload) should live in `haiv-lib/helpers/tui/` — shared territory both clients can see. It would be defined alongside the protocol, not in the IPC internals. The `CommandRequest` wraps it for transport, same as `WriteRequest` wraps `TuiModel`.

On the server side, the model loop gets a third branch:
```python
elif isinstance(request, CommandRequest):
    self._commands.modify(lambda cmds: cmds + [request.command])
    future.set_result(None)
```

And `drain_commands()` atomically swaps the list, same pattern as `drain_dirty()`.
