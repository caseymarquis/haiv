## Why I came here

The store dispatches signals per-section of `TuiModel`. I needed to see what those sections are and — critically — where git data lives relative to session data.

## What I found

Found the coupling. `SessionEntry` is a flat dataclass with both session identity (`id`, `mind`, `task`, `status`, `parent_id`) and git state (`ahead`, `behind`, `changed_files`) as peer fields. One object, two data sources.

The sections are:
- **HudSection** — role, worktree, summary, session (display-focused)
- **SessionsSection** — list of `SessionEntry` (the problem child)
- **ErrorsSection** — list of error strings

The model is `frozen=True` at the top level (section slots are stable), but sections themselves are mutable dataclasses. Each section inherits from `TuiModelSection` which presumably provides the `_version` int the store uses for diffing.

**The problem is clear now.** `SessionsSection` gets one version bump when *anything* changes — whether that's a session being added/removed or git counts updating. If git data is slow to fetch, either:
1. The whole section waits for git before updating (sessions display stale), or
2. Git data arrives partially and bumps the version with incomplete data (flakiness)

**What Casey's redesign looks like from here:** Split the git fields out of `SessionEntry`. Maybe a `GitSection` with its own entries keyed by branch or session ID. Sessions update when sessions change. Git updates when git changes. The widget merges them at render time by matching on session ID or branch.

**Also notable:** `TuiModel` lives in haiv-lib, not haiv-tui. So haiv-lib currently defines the *view shape* (what the TUI displays), not just the *data shape* (what the system knows). Casey's point about gather vs. assemble — haiv-lib is assembling a view model, not just providing raw data.

**Need to see:** `_base.py` for `TuiModelSection` (the version mechanism), and then wherever `SessionEntry` gets *populated* — that's where git calls are interleaved with session loading.

## Where to next?

- **`helpers.py`** or **`server.py`** — wherever SessionEntry gets built with git data. That's where gather and assemble are tangled.

Going to `_base.py` first — it's small and I need to understand the version/locking contract before I can reason about how to split things.
