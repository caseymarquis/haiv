## Why I came here

The atlas said "TuiStore — signal dispatch from model snapshots" and listed it as uncharted. Casey described the problem as "one locked model" that mixes data sources. I expected to find the model definition and the locking here.

## What I found

The store is *not* the model. It's a dispatcher. It holds a frozen `TuiModel` snapshot and fires blinker signals when section versions change. The actual intelligence is:

- **Version-based diffing** — each section has a `_version` int. Cheaper than value equality, race-free because versions come from the model thread.
- **Auto-discovered signals** — signals are generated from `dataclasses.fields(TuiModel)`. Add a field to TuiModel, get a signal for free.
- **Error isolation** — subscriber exceptions go to an `error_sink` callback, don't crash the poll loop.

The key import: `from haiv.helpers.tui.TuiModel import TuiModel`. The model lives in haiv-lib, not haiv-tui. That's where the data assembly happens and where the locking must be.

**Surprise:** I expected the store to be the bottleneck — the "one locked model" Casey described. But the store is just the delivery mechanism. The problem is upstream: in `TuiModel` itself and whatever builds it. The store's section-per-signal design actually *supports* the multi-source approach we want — if we can get TuiModel to have separate sections per data source, the store already knows how to dispatch them independently.

## Where this leads
