## Why I came here

Need to see `BranchStats` shape and what `branch_stats()` actually costs in subprocess calls.

## What I found

`BranchStats` is a dataclass: `ahead`, `behind`, `changed_files` — all ints, defaulting to -1. It has a `format()` method for display (arrows and checkmarks).

`branch_stats(branch, base_branch)` is expensive. Per session it makes:
1. `git worktree list --porcelain` — to find the worktree path for the branch
2. `git rev-list --count --left-right base...branch` — ahead/behind counts
3. `git status --porcelain` — changed file count

That's 3 subprocess calls per session. With 4 sessions, that's 12 git calls, all sequential, all inside `sessions_refresh`. And `worktree list` is called once per session even though the result is the same — it could be cached.

**The `quiet` flag matters.** `Git` prints every command it runs by default ("→ git rev-list..."). The TUI presumably creates git instances with `quiet=True`, but if not, the poll loop would be spamming the terminal.

**`at_worktree(branch)`** creates a new `Git` instance pointed at the worktree path. Each `branch_stats` call resolves the worktree path fresh. This is a natural cache point — worktree paths don't change between polls.

**The educational design is nice.** On failure, it prints the error and asks Claude to analyze it. The `intent` parameter adds human-readable context to error messages. This wrapper was built for minds to use, not just machines.

## Design implications for the split

`BranchStats` is already a standalone type — it doesn't reference sessions at all. A `GitSection` could literally be `dict[str, BranchStats]` keyed by branch name (or session ID). The data shape is ready; it's just the gathering that needs to move to its own cadence.

Optimization opportunity: call `worktree list` once, then `rev-list` and `status` per worktree. That cuts calls from 3N to N*2+1. But that's an optimization, not the architecture change.
