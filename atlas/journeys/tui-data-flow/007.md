**File:** `worktrees/main/haiv-tui/src/haiv_tui/widgets/sessions.py`

## Why I came here

Need to see the consumer side — what does the widget actually need from the data?

## What I found

Line 101 says it all: `stats = BranchStats(entry.ahead, entry.behind, entry.changed_files)`. The widget *reconstructs a BranchStats* from the flattened fields on `SessionEntry`, just to call `.format()`. The data went: git → BranchStats → flattened into SessionEntry → reconstructed as BranchStats → formatted as string. A round trip through a flat struct.

The widget subscribes to `store.sessions_changed` (line 71). When it fires, `_render_sessions` rebuilds the entire tree: clears children, builds parent/child hierarchy with `build_tree`, and constructs Rich `Text` labels with git stats appended as a suffix.

**The active mind highlight** is interesting — the widget asks the `TerminalManager` for the active mind name (line 83) and bolds that entry's label. This is *another* external data source mixed into the render, but handled correctly — it's queried at render time, not baked into the model.

**`action_launch_session`** calls `helpers.mind_launch` directly with the entry's mind name. It doesn't pass git — so mind launches from the TUI don't trigger git refresh. Only the command-side `mind_launch` in helpers.py does.

**The tree hierarchy** uses `build_tree` from `haiv.helpers.utils.trees` — a generic tree builder that takes `(item, parent)` pairs. It matches entries by `parent_id`. This is pure session data, no git involved.

## The full data flow is now mapped

```
CURRENT:
  sessions.ig.toml → load_sessions() ─┐
  git subprocess calls ────────────────┼→ SessionEntry (flat, mixed) → TuiModel.sessions
                                       │   → store signal → widget rebuilds tree
                                       │   → reconstructs BranchStats to format()
```

```
PROPOSED:
  sessions.ig.toml → load_sessions() → TuiModel.sessions (session data only)
  git subprocess calls ──────────────→ TuiModel.git (BranchStats by branch/id)

  widget subscribes to BOTH signals
  widget merges at render time: session tree + git lookup for labels
```

The widget code barely changes — instead of pulling stats from `SessionEntry` fields, it looks them up from the git section by session ID or branch name. `BranchStats` already has `.format()`. No reconstruction needed.
