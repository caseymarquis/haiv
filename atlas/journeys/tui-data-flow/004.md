## What I found

Minimal. `TuiModelSection` is just a `_version: int` base class. The real mechanism is in the `ModelClient` protocol: `read() -> TuiModel` and `write(mutator: Callable[[TuiModel], None])`. Two implementations exist: `TuiClient` (presumably IPC) and `TuiLocalClient` (presumably in-process).

The `write()` mutator pattern is important — you pass a function that modifies the model in place, and presumably the client handles locking and version bumping. This means callers don't deal with concurrency directly.

**For the redesign:** The mutator pattern works fine with multiple sections. A git-refresh mutator would only touch a `GitSection`, a session-refresh mutator would only touch `SessionsSection`. They can run independently. The version on each section would only bump when that section's data actually changes. The store's per-section signal dispatch already handles the rest.

The architecture is more ready for this split than I expected. The hard part isn't the locking or signaling — it's the data assembly in helpers.py (or wherever `SessionEntry` gets populated with git data).
